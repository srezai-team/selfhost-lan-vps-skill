# Ubuntu ПК → домашний сервер

Агент настраивает машину (по SSH или локально), владелец делает физическую часть и звонит провайдеру. Работа идёт в паре: после каждого шага владелец подтверждает одной строкой, агент проверяет со своей стороны.

**Определение готовности:** сервер живёт в LAN по кабелю, SSH — только по ключам с ограничением по подсети, защита по чек-листу Фазы 3 пройдена, при запросе — сервис отдаётся в интернет по HTTPS (Фаза 4), у владельца на руках паспорт, журнал решений и список оставшихся ручных шагов (Фаза 5).

## Правила, которые не нарушаются

1. **Список сервисов сначала.** До изменений выясни, что должно работать (веб, n8n, файлы, БД, мониторинг) и что владелец готов сломать. Настраивай ровно это, без «заодно».
2. **Доступ дороже скорости.** Перед сетевой правкой — резервная копия и **страховка**: отложенный откат на случай потери связи. Если доступ идёт через туннель, правка не должна его рвать (Фаза 2).
3. **Один адрес — один интерфейс.** Один и тот же IP на кабеле и Wi-Fi валит маршрутизацию. Резервный канал — отдельный адрес и большая метрика.
4. **Снаружи проверяй снаружи.** Внешний доступ подтверждается запросом с другой машины/сети, а не `curl` с того же хоста.
5. **Секреты не в документы.** Пароли — в менеджер паролей владельца; в документах пиши только где он лежит.
6. **Отчёт после фазы:** что сделано → чем проверено → что осталось.

## Фаза 0. Разведка

Собери факты о машине:

```bash
. /etc/os-release; echo "$PRETTY_NAME"; uname -r
ip -br a; ip route
ls -l /etc/netplan/ && sudo netplan get
ss -tlnp; systemctl --failed --no-legend
free -h; df -h /; lsblk -o NAME,SIZE,TYPE,MOUNTPOINT
sudo ethtool <LAN_IFACE> | grep -E "Speed|Duplex|Link detected"
```

Спроси владельца: провайдер и тип подключения (договор), есть ли статический IP, чей роутер и есть ли к нему доступ, что должно работать на сервере, есть ли монитор/клавиатура и готов ли он звонить в поддержку (скрипт звонка — [`references/client-protocol.md`](references/client-protocol.md)).

**Готово, когда:** известны ОС и ядро, основной аплинк и скорость линка, LAN-подсеть/шлюз/DHCP-пул, адреса на интерфейсах, роутер и наличие доступа, тип подключения и статический IP, целевые сервисы, план физического доступа.

## Фаза 1. Кабель (делает владелец)

Схема: устройство провайдера (ONT/модем) → **WAN** роутера; ПК → **LAN**-порт роутера. Патч-корд Cat5e/Cat6; ПК в WAN/ONT напрямую не подключаем.

Проверка: `sudo ethtool <LAN_IFACE> | grep -E "Speed|Duplex|Link detected"` → `1000Mb/s`, `Full`, `yes`. Если 100Mb/s — кабель или порт роутера; если `no` — порт/кабель/драйвер.

**Готово, когда:** линк 1000 Full, MAC кабельного интерфейса записан, владелец подтвердил, какой порт занят.

## Фаза 2. Сеть: статический адрес, резерв и откат

Подробно — [`references/network-cutover.md`](references/network-cutover.md). Коротко:

1. Резервная копия `/etc/netplan` (и профиля NetworkManager, если он рендерер).
2. Статический адрес на кабельный интерфейс **вне DHCP-пула** (или резервация по MAC в роутере).
3. Wi-Fi — резерв: отдельный адрес, default-route с метрикой 700; ARP-flux приглушить sysctl.
4. Страховка: `systemd-run --on-active=180` с восстановлением бэкапа; применение — detached, чтобы разрыв SSH не прервал операцию.
5. Проверки: `ip -4 -br a`, `ip route`, `ip route get 1.1.1.1`, `ping <GW>`, DNS, внешний IP, состояние туннеля/сервисов.
6. Подтвердить результат и снять страховку.

**Готово, когда:** один default-route через кабель, `ip route get 1.1.1.1` идёт через кабельный интерфейс, DNS резолвит, внешний IP ожидаемый, резервный канал отвечает, страховка снята.

## Фаза 3. Минимальная защита

Чек-лист с командами проверки — [`references/hardening.md`](references/hardening.md). Группы: SSH (ключи, пароль и root запрещены, `AllowUsers`), UFW (default deny, доступ к 22 только из LAN), fail2ban, автообновления, время/NTP, sysctl, лимиты journald, Docker (логи, live-restore, публикация только на 127.0.0.1), бэкапы, heartbeat-мониторинг, BIOS/WoL.

**Готово, когда:** каждый пункт чек-листа PASS, `systemctl --failed` пуст, вход по паролю не проходит (проверено с другой машины), правила UFW не отрезают текущий доступ, бэкап проверен восстановлением хотя бы одного файла.

## Фаза 4. Внешний доступ (только если просили)

Подробно — [`references/external-access.md`](references/external-access.md). Порядок: топология (WAN-адрес роутера!) → при двойном NAT мост/DMZ от провайдера → проброс портов → UFW → DNS-запись → Caddy + Let's Encrypt → проверка снаружи.

**Готово, когда:** с внешнего хоста `curl -I https://<DOMAIN>` отдаёт ожидаемый код, сертификат валиден, наружу открыт только нужный порт, пароль/авторизация на сервисе не отключены, есть короткая инструкция «как откатить».

## Фаза 5. Сдача

Рядом с рабочей папкой создай четыре документа (пример структуры — [`references/handover-docs.md`](references/handover-docs.md)): `SERVER-STATUS.md` (паспорт: железо, сеть, доступы, ПО), `SERVER-HANDOFF.md` (что сделано, что осталось, грабли), `SERVER-HISTORY.md` (журнал решений: дата · вопрос · решение · почему · когда пересмотреть), `SERVER-NEXT-STEPS.md` (ручные шаги владельцу: BIOS, звонки, DNS).

Итоговое сообщение владельцу — 6 строк: что работает, как проверено, что осталось, где доступы, как откатить, что читать.

**Готово, когда:** документы лежат в рабочей папке, в них есть все шесть блоков, и владелец получил короткое резюме, а не пересказ команд.

## Ловушки

Каталог «симптом → причина → что делать» — [`references/pitfalls.md`](references/pitfalls.md). Самое дорогое: дубль IP на двух интерфейсах; приватный хоп в трассировке ≠ двойной NAT; перезапуск firewall на роутере рвёт NAT и вместе с ним доступ; Docker обходит `ufw`.

## Если доступа к машине нет

Режим «только инструкции»: выдавай владельцу готовые блоки для копирования целиком, проси присылать вывод команд, никогда не проси пароли в чат. Пункты «Готово, когда» проверяются по присланному выводу.
