# Внешний доступ: от NAT до HTTPS

Порядок жёсткий: топология → провайдер → проброс → firewall → DNS → TLS → проверка снаружи. Нарушение порядка даёт ложные выводы (например, «провайдер режет порты», когда проброса просто нет).

## 1. Топология: где живёт публичный IP

```bash
ip route                       # шлюз — адрес роутера
curl -s https://ifconfig.me    # внешний адрес, который видят сервисы
```

Дальше нужен **WAN-адрес роутера** (админка роутера → статус/настройки WAN):

| WAN-адрес роутера | Что это значит | Что делать |
|---|---|---|
| публичный (`<PUBLIC_IP>`) | мост/один NAT на роутере | обычный проброс |
| приватный (`10.x`, `100.64.x`, `192.168.x`) | двойной NAT (или CGNAT) | мост/DMZ у провайдера |

**Ловушка:** приватный хоп в `traceroute` **не доказывает** двойной NAT — это часто служебная сеть провайдера. Решает только WAN-адрес роутера.

Если доступа к роутеру нет — единственный честный вывод «неизвестно», и дальше либо доступ к роутеру, либо обходной путь.

## 2. Что просить у провайдера

Скрипт звонка и таблица ответов — [`client-protocol.md`](client-protocol.md). Результат: либо **bridge** (+ данные PPPoE, если он используется), либо **DMZ** на WAN-адрес роутера. CGNAT — проброс невозможен, только обходной путь (раздел 7).

## 3. Проброс портов

Общая таблица (любой роутер): внешний порт → внутренний IP:порт, протокол.

| Имя | Внешний порт | Внутренний IP | Внутренний порт | Протокол |
|---|---|---|---|---|
| web-80 | 80 | `<SERVER_IP>` | 80 | TCP |
| web-443 | 443 | `<SERVER_IP>` | 443 | TCP |

Правила: только нужные порты; сервис слушает на сервере; `NAT loopback` включать не обязательно (проверять снаружи); адрес сервера закрепить резервацией DHCP.

Пример для встроенных прошивок на Linux (Wive-NG и подобные) — проброс хранится в nvram, правила генерируются скриптом:

```bash
# формат: интерфейс, протокол(1 TCP/2 UDP/3 TCP&UDP), src-порт от, src-порт до,
#          dst IP, dst-порт от, dst-порт до, NAT-loopback, комментарий
nvram_set 2860 PortForwardEnable 1
nvram_set 2860 PortForwardRules "WAN,1,80,80,192.168.1.120,80,80,0,web-80;WAN,1,443,443,192.168.1.120,443,443,0,web-443;"
nvram_geniptablesrules 2860
cat /etc/portforward /etc/portforward_access   # проверить сгенерированное
/etc/portforward <PUBLIC_IP> && /etc/portforward_access   # применить только дельту
```

Не перезапускай firewall целиком: если что-то пойдёт не так, потеряешь NAT и доступ к серверу. Применяй только добавленные правила.

## 4. Firewall сервера

```bash
sudo ufw allow 80/tcp && sudo ufw allow 443/tcp
sudo ufw status numbered
```

## 5. DNS

A-запись `<SUBDOMAIN>.<DOMAIN>` → `<PUBLIC_IP>`, TTL 300–600.

**Проверка:** `dig +short <SUBDOMAIN>.<DOMAIN>` отдаёт публичный IP (с нескольких резолверов: `dig +short @1.1.1.1`).

## 6. Caddy + Let's Encrypt

Ubuntu-пакет проще (в репозитории 24.04+ есть caddy 2.x); официальный репозиторий — если нужна свежая версия:

```bash
sudo apt-get install -y caddy
sudo tee /etc/caddy/Caddyfile >/dev/null <<'CONF'
<DOMAIN> {
	encode gzip
	root * /var/www/<SITE>
	file_server
	# либо прокси на локальный сервис:
	# reverse_proxy 127.0.0.1:5678
}
CONF
sudo caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
sudo systemctl restart caddy
```

Проверка локально: `curl -sI http://127.0.0.1/`. Сертификат выпускается автоматически, когда DNS уже указывает на публичный IP и снаружи доступен 80 (HTTP-01) или 443 (TLS-ALPN-01).

Если 80 заблокирован провайдером: DNS-01 через API DNS-провайдера (в Caddy — плагин) или TLS-ALPN на 443.

## 7. Проверка снаружи (обязательна)

С хоста вне домашней сети:

```bash
curl -sI https://<DOMAIN>            # ожидаемый код (200/302/401 — по сервису)
echo | openssl s_client -connect <DOMAIN>:443 -servername <DOMAIN> 2>/dev/null | openssl x509 -noout -issuer -dates
nc -zv <PUBLIC_IP> 22 80 443         # открыто ровно то, что нужно
```

Дополнительно: сертификат не самоподписанный; лишние порты закрыты; на публичном сервисе включена авторизация, если он не предназначен для всех.

## 8. Обходной путь без проброса

VPS с публичным IP + обратный SSH-туннель с сервера:

```bash
# на сервере: публикуем локальный 80 на VPS
ssh -N -R 127.0.0.1:8090:127.0.0.1:80 <TUNNEL_USER>@<VPS>
# на VPS: Caddy/nginx проксирует домен на 127.0.0.1:8090
```

TLS выпускается на VPS, трафик идёт через туннель. Работает при любом NAT и CGNAT; минус — зависимость от VPS и лишний хоп. Туннель оформить systemd-юнитом с `Restart=always`.
